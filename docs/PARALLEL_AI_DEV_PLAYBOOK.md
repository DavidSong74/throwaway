## 1. The product idea and the role of each platform

**Your proposed product:** Before changing an important development branch, launch three or four isolated attempts to implement the *same software requirement*. Each attempt writes code, runs tests, and produces a preview. A human reviews the variants and chooses one to promote to a pull request.

| Component | What it supplies | What it does **not** automatically supply |
|---|---|---|
| **Daytona** | 2–4 isolated cloud sandboxes, filesystems, processes, test/build execution, potential web preview ports | AI reasoning; automatically selecting the best code |
| **Nosana** | GPU-backed inference for the AI model(s) that generate edits, either via hosted per-token inference or your own Ollama deployment | A coding agent loop, code execution, repository awareness by itself |
| **Orchestrator (your Python app)** | Assigns each sandbox its work, calls Nosana, runs tests, captures diffs and artifacts, limits attempts | A fully featured UI until you build one |
| **GitHub** | A shared immutable starting commit, review branches, pull requests, merge history | Sandboxed execution or independently generated versions |
| **Human reviewer** | Product preferences, UX judgment, security review, final merge authorization | Should not be replaced by one raw LLM score |

**Important distinctions:**

- **3 sandboxes ≠ 3 distinct AI models.** You can call one model from three independent agent sessions, or configure three different model IDs if Nosana serves them.
- **Parallel code execution ≠ parallel model inference.** One self-hosted GPU may queue simultaneous requests. Hosted inference may offer more flexible model choices.
- **A task prompt ≠ an agent.** A true coding agent needs an *observe → plan → edit → execute → inspect → repeat* loop controlled by your application.
- **Start from a commit SHA**, not a moving branch name. Changes generated by candidates need **not** be committed or uploaded to GitHub before evaluation.

## 2. Architecture and the end-to-end workflow

```text
                 PROMPT + IMMUTABLE BASE COMMIT (SHA)
                              |
                        ORCHESTRATOR
                              |
              +---------------+---------------+
              |               |               |
        Candidate A     Candidate B     Candidate C
        Daytona VM      Daytona VM      Daytona VM
        clone SHA       clone SHA       clone SHA
              |               |               |
             model calls via Nosana inference endpoint(s)
              |               |               |
         edit & test     edit & test     edit & test
              |               |               |
       source + diff   source + diff   source + diff
              +---------------+---------------+
                              |
                    COMPARISON / REVIEW
                 tests + quality + UI preview
                              |
                   HUMAN SELECTS A WINNER
                              |
                     candidate Git branch
                              |
                     pull request → merge
```

**Canonical run sequence:**

1. Choose a public test repository and record its full 40-character **base commit SHA**.
2. Define a **task specification** and a **trusted test command**.
3. Start one Daytona sandbox for each candidate. Clone and checkout the same SHA in each.
4. Give the task, source context, and guardrails to the AI model via Nosana.
5. Save the proposed edit inside each isolated sandbox.
6. Run tests and optionally allow a bounded repair attempt.
7. Export code, logs, and `git diff` **before deleting sandboxes**.
8. Compare objective checks and subjective quality; choose a version.
9. Reproduce the winning patch locally; review, commit to a new branch, and create a PR.
10. Stop any unneeded Nosana deployment and confirm Daytona sandbox cleanup.

## 5. Pick your Nosana inference path

### Path A — Recommended: Nosana's hosted inference API

This avoids your own continuously allocated GPU and lets you select from currently available models.

**1. List live models** (read the `id`, `available`, `context_length`, `max_output_tokens`, `pricing`):

```bash
curl -sS https://inference.nosana.com/v1/models \
  -H "Authorization: Bearer $NOSANA_API_KEY" \
  | python3 -m json.tool
```

**2. Pick a model ID from the actual response**, ideally an instruction-following/coding-capable model. Do **not** copy a fictional model ID from an example.

```bash
export NOSANA_BASE_URL="https://inference.nosana.com/v1"
export NOSANA_MODEL_IDS="YOUR_ACTUAL_MODEL_ID,YOUR_ACTUAL_MODEL_ID"
```

Repeating one model is fine: it creates **two separate attempts** with identical requirements. This does **not** guarantee visually different implementations. Later you can use `MODEL_A_ID,MODEL_B_ID,MODEL_C_ID`, but only if each is currently available.

**3. Sanity test one inference request:**

```bash
python3 - <<'PY'
import os
from openai import OpenAI
client = OpenAI(base_url=os.environ["NOSANA_BASE_URL"], api_key=os.environ["NOSANA_API_KEY"])
model = os.environ["NOSANA_MODEL_IDS"].split(",")[0]
r = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "Reply with only the word READY"}],
    max_tokens=30,
)
print(r.choices[0].message.content)
print("token usage:", r.usage)
PY
```

A successful reply confirms an actual model endpoint works. For reasoning models, the output might not literally be `READY`; the important sign is a successful response.

### Path B — Optional: use your existing Nosana Ollama deployment

You previously created a deployment on an **RTX 3090**, exposing Ollama at port **11434**. Earlier the endpoint returned **Service Initializing**, so verify it again **before** connecting an agent:

```bash
export NOSANA_DEPLOYMENT_URL="https://YOUR-NOSANA-DEPLOYMENT-ENDPOINT"

curl -sS -i --max-time 20 "$NOSANA_DEPLOYMENT_URL/api/tags"
```

Interpret the response:

- `503` or HTML saying *Service Initializing* → review Nosana job logs, startup command, and container readiness. A job in `Running` state does not prove the server is healthy.
- `200` with `"models":[]` → Ollama is running but no model is installed; configure a model pull and ensure there is enough VRAM/disk.
- `200` with names → select an installed model.

After `/api/tags` lists a model, configure the OpenAI-compatible route exposed by Ollama:

```bash
export NOSANA_BASE_URL="$NOSANA_DEPLOYMENT_URL/v1"
export NOSANA_MODEL_IDS="EXACT_INSTALLED_MODEL_NAME,EXACT_INSTALLED_MODEL_NAME"
# Ollama commonly ignores the API key field, but the OpenAI client requires a value.
export NOSANA_API_KEY="ollama"
```

**Warning:** A public Ollama endpoint may not enforce authentication. Anyone who knows the URL may be able to call it. Avoid sensitive repositories and stop the deployment when finished. Check whether your Nosana configuration permits restricting access or placing authentication in front of the service. Your deployment's startup behavior and storage persistence must be configured separately.

**Recommended choice on $10:** Path A first. Stop an unnecessary self-hosted deployment rather than leaving an RTX 3090 idle.

## 6. Test Daytona independently

Before launching multiple instances, verify that your API key creates and cleans up one sandbox.

Create `test_daytona.py`:

```python
from daytona import Daytona

with Daytona() as daytona:
    sandbox = daytona.v2.create(cpu=2, memory=4, disk=8, wait_seconds=60)
    try:
        result = sandbox.exec("python3 -c 'print(2 + 3)'")

        daytona.v2.delete(sandbox)
```

Run:

```bash
python3 test_daytona.py
```

Expected: exit code `0`, output `5`, and **no leftover sandbox** in your Daytona dashboard. If the create fails, check API key permissions, project access, quotas, and SDK version first.

## 8. Run the parallel comparison

From the bundle root, with the virtual environment active and environment variables set:

```bash
# Beginner defaults: 2 candidates, each gets at most 2 inference calls
export MAX_REPAIRS=1
export MAX_OUTPUT_TOKENS=2400
export TEST_TIMEOUT_SECONDS=90

python3 parallel_candidates.py
```

The program launches both candidates **concurrently**. Each candidate does the following:

1. `daytona.v2.create()` creates a 2-vCPU, 4-GiB sandbox.
2. `git clone` copies your test repo into `/workspace`.
3. `git checkout --detach $BASE_SHA` ensures the same starting point.
4. Daytona reads `calculator.py`.
5. Nosana generates a full replacement for **that one Python source file**.
6. Daytona writes the proposed file and runs your test command.
7. On a failure, Nosana receives the previous source and test output and gets **one repair attempt**.
8. Daytona exports `git diff`, the final source file, test logs, and a JSON result.
9. The program asks Daytona to delete the sandbox in a `finally` block.

Example output **shape** (not a real run):

```text
Comparing 2 independently generated edits at e9c3f44a12b1
Per-agent inference call cap: 2; total: 4
[candidate-1] Creating Daytona sandbox
[candidate-2] Creating Daytona sandbox
[candidate-1] Cloning ...
[candidate-2] Cloning ...
[candidate-1] Nosana inference attempt 1
[candidate-2] Nosana inference attempt 1
[candidate-1] Running trusted tests
[candidate-2] Running trusted tests
[candidate-1] Sandbox deleted
[candidate-2] Sandbox deleted
Candidate results:
  candidate-1    model=...  passed=True  error=-
  candidate-2    model=...  passed=True  error=-
Review: results/20261115T...
```

### Files to inspect

```text
results/<UTC-run-id>/
  summary.json
  candidate-1/
    proposed_file.py      # candidate's complete replacement file
    changes.diff          # its Git diff against the BASE_SHA
    tests.log             # stdout/stderr from trusted test command
    result.json           # pass/fail, model, token counts, errors
  candidate-2/
    proposed_file.py
    changes.diff
    tests.log
    result.json
```

To inspect the differences between candidates:

```bash
# Replace RUN_ID with the actual folder printed by the script
RUN_ID="20261115T000000Z"
diff -u "results/$RUN_ID/candidate-1/proposed_file.py" \
        "results/$RUN_ID/candidate-2/proposed_file.py" || true
```

If both agents return the same code, that is a valid result. To create meaningfully different approaches, either select two different available model IDs or run **controlled experiments** with different design constraints (but then they do not receive literally identical prompts).

### Why this prototype is intentionally narrow

It proves **independent sandbox execution + LLM editing + objective tests + comparison + cleanup** without relying on model tool-calling support. It does **not** yet:

- modify multiple files or navigate arbitrary large repositories;
- repeatedly run arbitrary shell commands chosen by the AI;
- launch React app previews;
- create pull requests automatically;
- verify security or accessibility comprehensively;
- impose a hard dollar budget at the provider level.

Those are the next phases, not invisible features of the starter script.

## 9. Evaluate candidates and select a winner

Start with *hard gates* before judging aesthetics:

- [ ] Same base commit SHA for every candidate
- [ ] Original test files were not modified
- [ ] Test suite passed (or failures are clearly explained)
- [ ] No secrets, destructive code, unexplained network calls, or dependency surprises
- [ ] Build/lint passed where applicable
- [ ] Diff affects only expected parts of the repository

Then use a scoring rubric. Example for a frontend app:

| Category | Weight | Evaluation question |
|---|---:|---|
| Requirement coverage | 30% | Did it implement every requested behavior? |
| Functional correctness | 30% | Build, tests, interactions, regression behavior |
| UX / visual quality | 25% | Which UI is clearer, responsive, and consistent? |
| Maintainability | 15% | Is the code understandable and easy to extend? |
| Security | **Pass/fail gate** | Are there obvious vulnerabilities or unsafe changes? |

**Do not give a variant a passing security score merely because the tests passed.** Automated tests are necessary but insufficient.

For the tiny calculator prototype, use objective measures first: passing tests, minimal diff, readable implementation, no unrelated changes. For a dashboard redesign, add screenshots, interaction tests, accessibility checks, and live previews.

Store a short decision record:

```markdown
# Run decision
- Base SHA:
- Requested change:
- Candidate A: tests / strengths / weaknesses
- Candidate B: tests / strengths / weaknesses
- Winner and why:
- Human reviewer:
- Follow-up issues:
- PR link:
```

## 10. Turn the prototype into a true app-building agent

A real coding agent must be able to **discover project structure, inspect relevant files, edit multiple files, run tools, observe errors, and iterate**. This requires a tool-calling or structured-action loop in your *orchestrator*.

### Suggested tools per agent

| Tool | Purpose | Safety constraint |
|---|---|---|
| `list_files(path)` | Discover source files | Restrict path to sandbox repo |
| `read_file(path)` | Get code context | Restrict size; avoid secrets |
| `search_repo(query)` | Find definitions/usages | Limit result length |
| `write_file(path, content)` | Apply requested edits | Allowlist paths; reject traversal |
| `run_command(command_id)` | Execute predefined build/test/lint commands | Choose from an operator-maintained allowlist |
| `get_diff()` | Inspect what changed | Exclude secrets and generated binaries |
| `finish(summary)` | End attempt with an explanation | Must pass final independent evaluation |

**Avoid a tool called `run_any_shell_command` in the initial agent.** It is tempting but gives untrusted AI generations broad execution privileges. Start with controlled commands and expand only after adding safety controls.

### Agent loop (design pseudocode, **not** a copy-paste implementation)

```python
for candidate in candidates:  # each has its own Daytona sandbox
    clone_the_same_git_sha(candidate.sandbox)
    context = inspect_repo_structure(candidate.sandbox)

    for step in range(MAX_AGENT_STEPS):
        action = call_model_on_nosana(
            task=task_spec,
            context=context,
            allowed_tools=tool_schema,
        )
        if action.name == "finish":
            break
        validate_action(action)       # paths, permissions, command allowlist
        observation = execute_in_daytona(candidate.sandbox, action)
        context = append_observation(context, observation)

    result = run_trusted_checks(candidate.sandbox)
    export_diff_preview_logs(candidate.sandbox)
```

Not every model served by Nosana supports native function/tool calls reliably. If the chosen model does not, use a validated structured JSON action format and reject malformed responses. Implement model timeouts, action count limits, file-size limits, retries, context truncation, and error reporting.

### For React / Next.js app development

1. Build a fixed base image with Node, Git, and the required package manager.
2. Clone the *same* commit into each sandbox.
3. Run `npm ci` (or the appropriate lockfile-based install). This costs startup time: cache safe dependencies when possible.
4. Instruct agents to follow the existing framework, component library, lint rules, and tests.
5. Implement controlled multi-file edits.
6. Use trusted commands such as `npm run lint`, `npm test`, and `npm run build`.
7. Start each development server on a known port and obtain a Daytona preview endpoint.
8. Capture screenshots and compare UX manually; add Playwright checks if desired.
9. Export changes; **never** auto-merge merely because builds pass.

For large repositories, don't send every source file on each inference call. Give the model a repo map and targeted file reads; long prompts waste tokens and can exceed its context window.

After inspecting a winner, apply its exported diff to a **new branch** in a clean local clone at the same base commit.

```bash
# In a clean local copy of the same repository:
git checkout main
git pull --ff-only
git checkout -b review/ai-tournament-winner

# Check that your local HEAD still matches the recorded base SHA.

# Use the FULL path printed by the tournament script:
```

## 13. Security, reliability, and cleanup

### Before giving an AI agent access to a real repository

- **Use a disposable public test repo first.** Repository contents submitted to a Nosana model leave your local machine and the Daytona sandbox; understand the provider's data handling before using proprietary code.
- **Do not put `DAYTONA_API_KEY`, `NOSANA_API_KEY`, or a GitHub write token inside the agent's source context.** Keep API calls in the trusted orchestrator whenever possible.
- **Validate edit paths.** Reject `..`, absolute paths, `.git` edits, secret files, symlinks leaving the workspace, and unexpected binaries.
- **Control terminal commands.** Build/test commands may execute repository scripts; treat them as untrusted and run them only inside disposable, restricted sandboxes.
- **Limit networking.** Use Daytona network policy where supported. Remember that package installs may require carefully allowlisted network access.
- **Set timeouts and quotas.** Limit wall-clock runtime, agent steps, maximum output tokens, file sizes, and concurrent sandboxes.
- **Do not trust model-generated tests alone.** Run an independent trusted suite and security checks.
- **Capture audit metadata.** Base SHA, model ID, prompt version, candidate index, token usage, command output, test status, diff, cleanup result, reviewer decision.
- **No automatic merge** in early versions.

### Cleanup checklist after every run

- [ ] `parallel_candidates.py` reports **Sandbox deleted** for every candidate.
- [ ] Daytona dashboard shows no unintended running/stopped sandboxes still consuming resources.
- [ ] Nosana self-hosted deployment is stopped if not being actively used.
- [ ] Results files were exported before cleanup.
- [ ] Confirm current credits in both accounts.
- [ ] Remove accidental logs containing secrets, if any.

If the script reports **delete failed**, use the printed sandbox ID and manually delete it in the Daytona dashboard. If Python is interrupted abruptly (kill/power loss), `finally` cleanup may not complete: check the dashboard regardless.

## 14. Troubleshooting

| Symptom | Likely reason | What to do |
|---|---|---|
| Nosana `/api/tags` returns HTML Service Initializing | Ollama container/proxy isn't ready | Examine job/container logs and startup instructions; verify port 11434 |
| Nosana returns `models: []` | No weights installed | Pull a model or use hosted inference |
| Hosted inference returns `401` | Missing/malformed API key | Check `NOSANA_API_KEY`; use `Bearer` authentication |
| Hosted inference returns `402` | Credits insufficient | Check live account balance / halt calls |
| Hosted inference returns `404 model_not_found` | Model not currently served | Re-list available model IDs |
| `max_tokens` unsupported | Model endpoint has different parameter support | Check model documentation; remove/adjust argument if needed |
| Daytona SDK doesn't have `.v2` | Wrong package version | `pip show daytona`; install version in `requirements.txt` |
| `git clone` fails in Daytona | Wrong public URL or network restrictions | Test public HTTPS clone and network policy |
| `git checkout` fails | Incorrect SHA / repository | Record full pushed SHA using `git rev-parse HEAD` |
| All candidates fail tests | Model misunderstood task, insufficient context, or baseline tests | Inspect `tests.log`, `result.json`, and code changes |
| Models return near-identical code | Same model + simple task | Try distinct served model IDs or a more open-ended task |
| Code was truncated | Response token limit too low | Try a smaller target file or increase cap carefully |
| No React preview | Starter script edits one Python file and deletes sandboxes | Implement Phase 2 preview lifecycle |
| Credit usage is unexpectedly high | Idle GPU or repeated inference calls | Stop deployment; check token usage and running resources |

## 15. Milestones and next sprint

### Phase 0 — Prove the APIs (about 10–20 minutes once accounts work)

- [ ] Nosana returns a successful single inference response.
- [ ] Daytona prints `5` inside a sandbox and deletes it.
- [ ] Both balances checked.

### Phase 1 — Two-way code tournament (about 20–45 minutes depending on setup)

- [ ] Public sample repository is on GitHub with a recorded SHA.
- [ ] Two sandboxes clone the same source.
- [ ] Two independent Nosana requests propose an edit.
- [ ] Both run the unchanged `unittest` suite.
- [ ] Diff, source, and logs are exported.
- [ ] Sandboxes are deleted, and a reviewer selects a winner.

### Phase 2 — Your first real app feature (roughly a small development sprint)

- [ ] Replace sample repo with a disposable React/Next.js repo.
- [ ] Add safe multi-file read/write and searching.
- [ ] Add an iterative agent loop with max steps and fixed commands.
- [ ] Add build, test, lint, and optionally Playwright checks.
- [ ] Produce a screenshot or authenticated preview per candidate.

### Phase 3 — Three/four candidates + GitHub workflow

- [ ] Accept three/four model assignments and concurrency controls.
- [ ] Store objective scores, review notes, and evidence per candidate.
- [ ] Compare versions side-by-side.
- [ ] Create a candidate branch or PR **only after explicit human approval**.
- [ ] Add model cost accounting, per-run budget limits, alerts, and automated stale-sandbox cleanup.

### Phase 4 — Production readiness

- [ ] Private repository onboarding with scoped permissions.
- [ ] Secure secret management, sandbox egress controls, audit trails.
- [ ] Retry and recovery of failed worker jobs.
- [ ] Artifact storage beyond sandbox lifetime.
- [ ] Reproducibility: pinned model version, prompt version, git SHA, dependency lockfile.
- [ ] Team review/approval and merge protections.

**Suggested first acceptance criterion:** Two independent candidates start from the same Git SHA, each modifies **only** `calculator.py`, both are evaluated by the **unchanged** tests, and their diffs can be inspected **after the sandboxes have been deleted**. This validates the architectural core before you build a full dashboard.
